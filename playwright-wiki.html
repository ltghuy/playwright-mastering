3-month roadmap · reference edition

From manual tester to Playwright automation

One concept, one code example, per step. Skim it as a wiki while you learn, or copy a snippet straight into your editor. Written for a QC who knows testing but is new to code.

Language TypeScript Pace ~8–10 hrs/week Duration 12 weeks Home base playwright.dev
01

Foundations

Weeks 1–3 · You can't master a tool built on JavaScript without a little JavaScript. Don't skip this.

JavaScript basicsweek 1

The raw materials: variables, arrays, objects, and functions. A test is just a function that does things and checks results — so this is the grammar everything else is written in.

Async / await & Promisesweek 2 · critical

Browser actions take time — a click, a page load, a network response. A Promise represents a value that isn't ready yet; await pauses until it is. This is the concept that unlocks Playwright.

Why it matters: almost every Playwright command returns a Promise. Forget one await and your test races ahead of the browser and fails in confusing, flaky ways.

TypeScript essentialsweek 2

TypeScript = JavaScript + types. Types catch mistakes as you type (autocomplete, red squiggles) instead of at runtime. You need only the basics; Playwright supplies the rest.

Project setupweek 3

Install Node.js and VS Code, then let Playwright scaffold everything — config, example tests, and the browsers — with one command.

Milestone: a Git repo on GitHub with one passing test. Learn git clone / add / commit / push now — you'll need it for CI later.
02

Playwright core

Weeks 4–7 · The real thing. Keep playwright.dev open in a tab.

Locatorsweek 4

A locator is how you point at an element. Prefer user-facing locators (getByRole, getByLabel, getByText) — they mirror how a real person and a screen reader find things, so they survive CSS refactors.

Actionsweek 4

What you do to a located element: click, type, check, choose. Each one auto-waits for the element to be ready before acting.

Assertions & auto-waitingweek 5 · key

Assertions verify the app did the right thing. Playwright's web-first assertions automatically retry until the condition is true or times out — which is why you almost never need manual sleeps.

Coming from manual testing: think of each expect as one written test-case step — "the cart should show 1 item" — but checked by the machine, on every run.

Debugging toolsweek 6

Playwright's tooling is its superpower. Codegen records clicks into code, UI mode runs tests visually with time-travel, and the Trace Viewer lets you replay a failure step-by-step after the fact.

Tip: set trace: "on-first-retry" in your config so failures always leave a trace to inspect.

Test structure & configweek 7

Group related tests with describe, share setup with hooks like beforeEach, and centralize settings — base URL, browsers, timeouts — in playwright.config.ts.

Data-driven testsweek 7

One scenario, many inputs. Loop over a data array to generate a separate test per case — your manual "test matrix", automated.

03

Professional patterns

Weeks 8–10 · Move from "writes tests" to "builds a framework".

Page Object Modelweek 8

Put each page's locators and actions in its own class. Tests read like plain English; when the UI changes, you fix one file instead of fifty.

API testingweek 9

Playwright talks to APIs too. Validate endpoints directly, or use the API to set up state fast before verifying it in the UI — far quicker than clicking through setup screens.

Auth reuse with storageStateweek 9 · huge time-saver

Log in once in a setup step, save the session to a file, then reuse it in every test. Your tests skip the login UI entirely and run much faster.

CI/CD with GitHub Actionsweek 10

Run the whole suite automatically on every push. Failures upload the HTML report and traces as artifacts you can download and replay.

Milestone: a green check ✔ on your commits — the signal that your tests protect the app on every change.
04

Capstone & mastery

Weeks 11–12 · Prove it by building something real and shareable.

🎯 Capstone: build a complete framework

Pick a real app — a demo store, or ideally something from work — and assemble everything above into one portfolio project you can show in interviews or bring to your team.

  • Structure: Page Object Model, tidy folders, a clear README explaining your design choices.
  • Coverage: 15–25 meaningful tests mixing UI and API flows.
  • Speed: auth reuse via storageState, data-driven cases, shared fixtures.
  • Automation: CI running on every commit, with reports and traces on failure.
  • Cross-browser: passing on Chromium, Firefox, and WebKit.

⚠ Pitfalls to avoid (especially from a manual background)

  • Don't automate everything. Automate stable, repetitive, high-value flows. Keep exploratory and UX testing manual — that judgment is your edge.
  • Never waitForTimeout to "fix" flakiness. Use web-first assertions that auto-retry; fix the real cause.
  • Don't lean on brittle CSS/XPath. Prefer role- and label-based locators that survive redesigns.
  • Read before you copy. Codegen and AI give you a starting point — understand each line, then refine it.
  • Code every session. 70% hands-on, 30% reading. Skill is built by typing, not watching.
